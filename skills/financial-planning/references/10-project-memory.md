# 项目中的长期财务记忆

只有用户明确需要长期维护，或当前任务显然会跨多次对话复核时，才在项目根目录建立固定文件夹 `.financial-plan/`。不要为一次性问题创建它，也不要扩散到项目其他位置。

文件夹最多保留四个 Markdown 文件：

- `overview.md`：家庭成员、司法辖区、规划范围、授权边界、价值排序和紧急联系人。
- `facts.md`：已核实的财务事实、来源日期、待核实事项和假设。
- `plan.md`：当前目标、诊断、决定、行动顺序、负责人、期限和触发条件。
- `history.md`：按日期记录重要变化、已执行事项、改判原因和下一次复核。

这是财务记忆，不是账务系统。不要创建脚本、数据库、程序配置、复杂模板或一堆分类文件；不复制完整身份证件、账号、密码、密钥、报税表或保单原件。原始敏感文件只记录用户认可的安全位置与必要摘要。

## 建立规则

先查看项目是否已有 `.financial-plan/` 或其他财务档案。若已有，沿用并避免重复。创建前告诉用户将建立这四个文件及用途；用户不同意则在对话内工作。

首次建立时主动问最小信息集：客户和受影响家庭成员；所在地与税务居民身份；前三个目标与期限；收入、必要支出、流动资产和债务概况；主要保险；近期重大期限；授权边界。用户不知道的内容写为待核实，不补猜。

## 写入规则

事实、假设、建议和已执行行动必须分开。每条重要事实注明“截至何日”和来源；估算注明区间；未见文件的内容注明“用户口述”。发现冲突时保留两种说法并列入待核实，不静默覆盖。

每次实质变化只更新相关段落，并在 `history.md` 留一条简短记录：日期、变化、原因、影响和下次复核。不要记录闲聊，不保存与财务规划无关的个人信息。

## 读取规则

新的财务任务开始时，若 `.financial-plan/` 存在，先读取四个文件，再问其中缺失或过期且会改变当前决定的信息。不要要求用户重复已经核实且仍有效的资料。

## 隐私与用户控制

默认不把财务档案提交版本库；若项目使用版本控制，提醒用户检查忽略规则，但不要擅自修改项目级配置。任何对外发送、上传或同步都需用户明确授权。

用户要求删除或停止维护时，先确认精确目标并说明会失去哪些历史，再执行可恢复的删除方式。不得借“维护”之名擅自交易、付款、开户、改受益人或联系第三方。
